Tour sécurité et retour global sur la qualité du code

Audit statique réalisé le 14 août 2026 sur l’état courant du workspace. Périmètre : API NestJS, bot Discord, dashboard Angular, package partagé, Docker et CI.

Verdict rapide

Base saine, mais pas encore durcie de bout en bout. Le projet possède de bonnes fondations de sécurité applicative et une architecture lisible. Le principal travail restant concerne le périmètre de déploiement, la validation explicite de la configuration de production, la couverture des chemins sensibles et la reproductibilité des images Docker.

Sécurité : points solides

Authentification

Guard JWT global avec ouverture explicite par @Public(). Mots de passe hachés en Argon2id, hachage factice contre l’énumération temporelle, verrouillage après échecs et limite dédiée de 5 connexions/minute sur le login.

Références : api/src/auth/auth.service.ts, api/src/auth/auth.controller.ts, api/src/app.module.ts

Sessions

Access token court gardé côté application, refresh token opaque en cookie httpOnly, secure en production et rotation avec révocation des jetons réutilisés.

Référence : api/src/auth/token.service.ts

Entrées et API

ValidationPipe global avec transformation contrôlée, whitelist et forbidNonWhitelisted. Helmet, CORS explicite et throttling global sont présents.

Références : api/src/main.ts, api/src/app.module.ts

Données

Prisma est utilisé presque partout. Le seul SQL brut repéré dans la recherche membres paramètre les valeurs et protège les colonnes de tri par une table blanche.

Référence : api/src/members/members.service.ts

Risques et corrections proposées

Priorité Constat vérifié Impact Correction recommandée
Élevée Les fichiers secrets existent localement. api/.env, bot/.env et packages/shared/.env sont présents, même s’ils ne sont pas suivis par Git. Une copie, archive, capture ou mauvaise commande peut exposer base, JWT ou token Discord. Conserver uniquement les .env.example dans le dépôt, vérifier l’historique Git et les artefacts CI, utiliser les secrets Coolify, et faire tourner toute valeur ayant déjà été partagée.
Élevée La production ne valide pas explicitement CORS et cookie. COOKIE_SECURE est configurable et CORS_ORIGINS est construit depuis APP_DOMAIN, sans contrôle HTTPS/wildcard dans configuration.ts. Une erreur de déploiement avec cookies credentials peut élargir l’origine autorisée ou diminuer le transport sécurisé. En production, refuser les origines non HTTPS, les wildcards et les valeurs vides ; imposer cookieSecure=true et ajouter des tests de configuration négatifs.
Moyenne Le serveur Nginx ne déclare pas de headers de sécurité. Le fichier ne contient que le fallback Angular. CSP, HSTS, anti-framing et options de type MIME dépendent du proxy amont et peuvent manquer selon l’environnement. Définir une CSP compatible avec Angular, HSTS uniquement derrière HTTPS, X-Content-Type-Options et une politique de framing ; vérifier les headers avec un test d’intégration.
Moyenne Les limites sont bonnes mais peu spécialisées. Le login est limité, tandis que le throttling par défaut est de 120 requêtes/minute pour toutes les routes. Les recherches lourdes, exports ou endpoints publics peuvent consommer une part disproportionnée des ressources. Définir des profils par endpoint (auth, recherche, écriture, health), idéalement avec un stockage partagé si plusieurs réplicas API sont déployés.
Moyenne La couverture de sécurité n’est pas démontrée par un seuil. Les tests passent, mais aucun seuil de couverture n’est imposé dans les scripts ou la CI. Les guards, DTO, rotation de refresh tokens, commandes Discord et synchronisations peuvent régresser sans alerter. Ajouter tests ciblés pour JwtAuthGuard, PermissionsGuard, PasswordChangeGuard, auth/refresh, recherche SQL et commandes de modération ; publier et imposer un seuil progressif.
Moyenne Les images runtime ne fixent pas d’utilisateur non privilégié. Les Dockerfiles ne contiennent ni USER ni durcissement explicite du système de fichiers. Une compromission applicative aurait un périmètre plus large dans le conteneur. Créer un utilisateur runtime dédié, passer les répertoires nécessaires en lecture seule, ajouter un HEALTHCHECK et limiter les capabilities au niveau Compose.
Faible Le build du bot utilise npm install. Les autres images utilisent aussi des étapes distinctes et le bot reste hors workspace. Moins de reproductibilité et risque de dérive par rapport au lockfile lors d’une reconstruction. Copier bot/package-lock.json et utiliser npm ci dans l’image ; aligner cette règle avec la CI.
Faible Audit npm : une vulnérabilité modérée est signalée dans chaque arbre audité. Aucune high/critical n’a été trouvée. Risque limité, mais les dépendances transitives restent à suivre. Examiner les avis modérés liés à echarts et undici, puis ajouter périodiquement npm audit --audit-level=high ou Dependabot en CI.

Qualité globale du code

Bon Architecture

La séparation API/bot/webapp/shared est nette. Les contrats partagés, les DTO et les décorateurs de permissions réduisent la duplication. Le graphe signale aucune boucle d’import détectée.

Bon Lisibilité

Les abstractions importantes sont nommées, les décisions sensibles sont documentées et les règles métier Discord complexes sont isolées dans des collecteurs et tâches dédiés.

À renforcer Tests

126 tests racine passent, ce qui est un bon filet de non-régression. Il faut toutefois compléter les chemins de sécurité, les contrôleurs et le bot, puis mesurer la couverture plutôt que compter seulement les suites.

À renforcer Exploitabilité

La configuration est typée et échoue tôt, mais le contrôle de ses invariants de production (CORS, HTTPS, secrets, intents Discord) devrait être aussi strict que le contrôle des variables obligatoires.

À renforcer Reproductibilité

La CI construit et teste les principaux composants, mais le bot est hors workspace et son Dockerfile utilise npm install. Les audits de dépendances et les scans d’image ne sont pas encore des étapes bloquantes.

Bon Dette technique

Le code ne montre pas de cycle d’import et concentre correctement le SQL brut dans un point justifié. La priorité est la couverture et le durcissement, pas une refonte de l’architecture.

Plan d’action suggéré

  1. Avant mise en production : valider CORS/HTTPS/cookies, vérifier les secrets locaux et historiques, ajouter un utilisateur non root aux images, puis tester les headers réellement servis.
  2. Prochaine itération : écrire les tests des guards et de l’authentification, couvrir la whitelist SQL et les commandes sensibles du bot, et instaurer un seuil de couverture.
  3. Industrialisation : remplacer npm install par npm ci dans le bot, ajouter audit dépendances et scan d’images en CI, et rendre les limites de débit configurables par environnement.

Limites de l’audit

Il s’agit d’une revue statique complétée par les tests racine et deux audits npm de production. Je n’ai pas inspecté le contenu des fichiers .env, effectué de test d’intrusion, vérifié la configuration réelle de Coolify/Traefik/Discord, ni exécuté la CI complète avec le test et le build séparés du bot. Le workspace contient aussi des modifications utilisateur non liées ; elles ont été laissées intactes.
